# 技術検証メモ — Bカート iOSアプリ化(WebView + プッシュ + 生体認証)

作成日: 2026-06-25
対象: Bカートの買い手(取引先)向けリピート発注を促進するiOSアプリ
方針: 既存のBカートサイトをWebViewで包み、プッシュ通知・生体認証ログインのネイティブ機能を最小限追加する

---

## 1. 結論サマリ

| 検証項目 | 結果 | 備考 |
|----------|------|------|
| WebViewでBカートを包めるか | ✅ 可能 | Bカートはレスポンシブ対応済み。スマホ表示が崩れない |
| プッシュ通知を実装できるか | ✅ 可能(中継サーバー必須) | BカートのWebhook → 自前サーバー → APNs の経路で実現 |
| 生体認証ログインを実装できるか | ✅ 可能 | 端末側でログイン情報を保護し、Face ID/Touch IDで解錠してWebViewへ注入 |
| Bカート単体でプッシュは出せるか | ❌ 不可 | Bカートはネイティブアプリ・標準プッシュを持たない(Webのみ) |

→ **「包む + プッシュ + 生体認証」は技術的に成立する。ただしプッシュには小規模な中継サーバーが1つ必要。**

---

## 2. Bカートが提供する連携機能

### 2.1 REST API(正式版)

- ドキュメント: https://docs.api.bcart.jp/ (V1)
- 取得/操作できる主なリソース: **受注・商品・会員・在庫・配送先** ほか
- 認証: **パーソナルアクセストークン**(スコープ指定可)または **OAuthクライアント**
  - リクエストは `Authorization: Bearer <token>` ヘッダーで送信
  - トークンは発行時に1回だけ表示されるため要保管
- レート制限: **300秒あたり300リクエスト**(超過すると300秒ロック)
- 後方互換性は基本維持(項目廃止時は旧項目を残し新項目を追加)

### 2.2 Webhook(β版)

- ドキュメント: https://userguide.bcart.jp/management/conf/external/webhook/
- 仕組み: Bカートで発生したイベントを、登録したエンドポイントURLへ **POST通知**
- 通知対象イベント: **受注情報・会員情報・配送先情報** の「新規登録」「更新」
- 実績: 新規注文時にSlack / Chatwork / Microsoft Teams / LINE へ通知する利用例あり
- 推奨パターン: 「Webhookで通知を受ける → 必要に応じてAPIで詳細データを取得」
- ⚠️ **重要な制約: 配信は保証されない(β版)**。取りこぼしの可能性があるため、重要通知はAPIポーリングで補完する設計が必要

### 2.3 スマホ表示

- Bカートはレスポンシブ対応済み(BtoB ECとして国内初採用)
- WebViewで表示してもレイアウトは崩れない前提で設計可能

## 3. プッシュ通知で「送れる/送りにくい」通知の整理

| 通知したい内容 | 実現方法 | 難易度 |
|----------------|----------|--------|
| ご注文を承りました | Webhook(受注 新規) → APNs | ◯ 容易 |
| 注文内容が変更されました | Webhook(受注 更新) → APNs | ◯ 容易 |
| 出荷しました / 配送状況更新 | Webhook(受注更新 or 配送先更新)でステータス変化を検知 → APNs | △ ステータス項目の判定ロジックが必要 |
| 新規会員登録の承認完了 等 | Webhook(会員 新規/更新) → APNs | ◯ 容易 |
| 再入荷しました | Webhookの対象外の可能性が高い → 商品/在庫APIを定期ポーリングして検知 | △ ポーリング実装が必要 |
| 定期発注リマインド(そろそろ発注時期です) | Webhookとは無関係。中継サーバー側で発注履歴をもとにスケジュール送信 | △ ロジック追加が必要だがリピート促進に最も効果的 |
| セール/お知らせの一斉配信 | 中継サーバーの管理画面から手動でブロードキャスト | ◯ 容易 |

ポイント: **リピート発注狙いなら「出荷通知」+「定期発注リマインド」+「再入荷通知」が主役。** いずれもWebhook単体では完結せず、中継サーバー側のロジック(ステータス判定/ポーリング/スケジューラ)が肝になる。

## 4. 生体認証ログインの方式

Bカートのログイン方式に依存するため、実装前に1点確認が必要。

| Bカート側の認証方式 | 想定実装 | 確実性 |
|---------------------|----------|--------|
| 通常のセッション(Cookie)ログイン | 端末のKeychainにID/パスワードを保管 → Face ID/Touch IDで解錠 → WebViewのログインフォームへ自動入力・送信 | ◯ 実現可能(一般的な手法) |
| API/SSO トークン認証がある場合 | トークンをKeychainで保護し、生体認証で解錠してWebViewへ注入 | ◎ より安全・確実 |

- iOSの `LocalAuthentication`(Face ID / Touch ID)+ `Keychain` で認証情報を保護
- パスワードを端末外に出さない設計にすればセキュリティ要件も満たしやすい
- ⚠️ 確認事項: Bカートのログインに **CAPTCHA や二要素認証** が挟まると自動ログイン注入が難しくなる。実画面で要確認

---

## 5. 実装前に確認すべきこと(チェックリスト)

- [ ] BカートのプランでAPI / Webhookが利用可能か(オプション扱い・上位プラン限定の可能性)
- [ ] Webhookで実際に飛んでくるイベント種別とペイロード項目(特に受注ステータスの表現)
- [ ] 「出荷完了」をどのイベント/項目で判定できるか
- [ ] 再入荷を検知するための在庫/商品APIの項目とポーリング頻度(レート制限300/300秒の範囲内に収まるか)
- [ ] ログイン画面の方式(セッション or トークン、CAPTCHA・2要素の有無)
- [ ] 会員IDとアプリのデバイストークンを紐付ける方法(ログイン成功時にアプリから中継サーバーへ登録する想定)
