# 最小構成の設計書 — Bカート iOSアプリ(WebView + プッシュ + 生体認証)

作成日: 2026-06-25
対象範囲: iOSのみ / 既存取引先のリピート発注促進

---

## 1. 全体構成

```
┌─────────────────────────────┐
│            iOS アプリ                      │
│  ┌───────────────────────┐ │
│  │ WKWebView                            │ │  ← Bカートのレスポンシブサイトを表示
│  └───────────────────────┘ │
│  ┌───────────────────────┐ │
│  │ 生体認証(Face ID / Touch ID)       │ │  ← Keychainのログイン情報を解錠しWebViewへ注入
│  └───────────────────────┘ │
│  ┌───────────────────────┐ │
│  │ プッシュ受信(APNs) + ディープリンク │ │  ← 通知タップで該当画面へ遷移
│  └───────────────────────┘ │
└─────────────┬───────────────┘
              │ ① 起動時/ログイン時: デバイストークン + 会員IDを登録
              ▼
┌─────────────────────────────┐
│        中継サーバー(自前・小規模)         │
│  - Webhook受信エンドポイント               │  ← ② BカートからのPOSTを受ける
│  - 会員ID ⇄ デバイストークン 対応表(DB)   │
│  - イベント判定(出荷完了など)             │
│  - 在庫ポーリング(再入荷検知 / 任意)       │
│  - 定期発注リマインドのスケジューラ(任意)   │
│  - APNs送信(JWT認証)                       │  ← ④ 対象端末へプッシュ
└──────┬───────────────┬──────┘
        │ ② Webhook(POST)  │ ③ 詳細取得(API / Bearer)
        ▼                  ▼
┌─────────────────────────────┐
│              Bカート                       │
│  - Webhook(受注/会員/配送先 の 新規・更新) │
│  - REST API(受注/商品/在庫/会員/配送先)    │
└─────────────────────────────┘
```

### データの流れ
1. アプリ起動・ログイン成功時、アプリが「APNsデバイストークン + Bカート会員ID」を中継サーバーに登録
2. Bカートでイベント発生 → Webhookが中継サーバーへPOST
3. 中継サーバーが必要に応じてBカートAPIで詳細を取得し、通知すべきか判定
4. 対象会員のデバイストークン宛にAPNsでプッシュ送信
5. ユーザーが通知タップ → アプリのWebViewが該当ページ(注文詳細など)を開く

## 2. コンポーネント別 仕様

### 2.1 iOSアプリ

| 機能 | 内容 |
|------|------|
| WebView表示 | `WKWebView` でBカートサイトを表示。プルリフレッシュ・戻る/進む・外部リンクをSafariで開く等の最低限のナビゲーション |
| 生体認証ログイン | 初回はユーザーが手動ログイン → 同意の上でID/パスワードをKeychainに保存。次回以降はFace ID/Touch IDで解錠しWebViewのフォームへ自動入力 |
| プッシュ受信 | 起動時にAPNs登録 → デバイストークン取得 → 中継サーバーへ送信。通知タップで対象URLをWebViewで開く(ディープリンク) |
| 会員ひも付け | ログイン成功を検知し、会員IDとデバイストークンを中継サーバーへ登録 |
| 最低限のネイティブ価値 | 審査(ガイドライン4.2)対策として、プッシュ・生体認証・(任意で)バーコード/カメラ発注などを備え「ただのWeb包み」にしない |

技術スタック: Swift / SwiftUI または UIKit、`WKWebView`、`LocalAuthentication`、`Security`(Keychain)、`UserNotifications`

### 2.2 中継サーバー

| 機能 | 内容 |
|------|------|
| Webhook受信 | BカートからのPOSTを受信・署名/トークン検証・冪等処理(重複イベント対策) |
| デバイス管理 | 会員ID ⇄ デバイストークンの対応表(1会員=複数端末を許容)。退会・トークン失効の掃除 |
| イベント判定 | 受注/配送先の更新ペイロードから「出荷完了」等を判定。送る/送らないのルール管理 |
| 補完ポーリング(任意) | Webhook対象外の再入荷などを、在庫/商品APIの定期取得で検知(レート制限300/300秒を遵守) |
| リマインド(任意) | 発注履歴をもとに「定期発注の時期」を算出しスケジュール送信 |
| APNs送信 | トークンベース認証(.p8キー / JWT)でAPNsへ送信。失敗トークンの除去 |
| 管理画面(任意) | お知らせの一斉配信、送信ログ確認 |

技術スタック例: Node.js or Go / 軽量DB(PostgreSQL等)/ APNs用 `.p8` キー。小規模VPSまたはマネージド(Cloud Run / App Runner等)で常時稼働

### 2.3 Bカート側の設定

- API用のパーソナルアクセストークンを発行(必要スコープ: 受注/商品/在庫/会員/配送先 の参照中心)
- Webhookエンドポイントに中継サーバーのURLを登録し、受注/会員/配送先の新規・更新を有効化
- ※プランによりAPI/Webhookがオプションの可能性 → 契約状況の確認が前提

## 4. 開発工数の概算

> 前提: 1人のエンジニアが実装。実装難度や確認事項の結果で増減します。あくまで初期見積もりのレンジです。

| フェーズ | 内容 | 概算工数 |
|----------|------|----------|
| 0. 事前確認・要件確定 | プラン/API/Webhook/ログイン方式の確認、通知仕様の確定 | 2〜4人日 |
| 1. iOSアプリ(WebView+ナビ) | WKWebView基盤、表示・遷移 | 4〜7人日 |
| 2. 生体認証ログイン | Keychain保存 + Face ID + フォーム注入 | 4〜7人日 |
| 3. プッシュ受信・ディープリンク | APNs登録、通知タップ遷移 | 3〜5人日 |
| 4. 中継サーバー(Webhook→APNs) | 受信・デバイス管理・送信・判定 | 7〜12人日 |
| 5. 補完機能(再入荷/リマインド) ※任意 | ポーリング・スケジューラ | 3〜6人日 |
| 6. App Store審査対応・申請 | アイコン/スクショ/プライバシー/申請・リジェクト対応 | 3〜5人日 |
| **合計** | | **約26〜46人日(目安 1.5〜2.5ヶ月)** |

最小スタート(MVP)なら、フェーズ5(任意)を後回しにして **約23〜40人日** から着手可能。

## 5. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| Webhook配信が保証されない(β版) | 通知の取りこぼし | 重要通知はAPIポーリングで二重化。冪等処理で重複も吸収 |
| App Store審査4.2(最小機能) | リジェクト | プッシュ+生体認証+(任意でカメラ発注)でネイティブ価値を確保 |
| ログインにCAPTCHA/2要素 | 自動ログイン困難 | 実画面で要確認。難しければ手動ログイン+セッション維持に切替 |
| Bカート仕様変更 | 連携停止 | 後方互換方針ありだが、Webhook/API変更の告知を監視 |
| レート制限(300/300秒) | ポーリング過多でロック | ポーリング頻度を設計時に試算し上限内に収める |

## 6. 推奨する進め方(マイルストーン)

1. **PoC(概念実証)**: 中継サーバーの雛形(Webhook受信 → APNs送信)を最小実装し、実機1台にプッシュが届くことを確認
2. **MVP**: WebView + 生体認証ログイン + 出荷通知プッシュ までを通しで実装し、社内テスト
3. **拡張**: 再入荷通知・定期発注リマインド・一斉配信を追加
4. **申請**: App Store審査 → リリース

次アクションとして、フェーズ0の「事前確認」を一緒に潰すか、PoCの中継サーバー雛形コードの作成から着手できます。
